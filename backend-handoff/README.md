# Пакет для бэкенда

Готовые материалы из фронт-репозитория, чтобы не выводить контракты вручную.
Всё сгенерировано из работающего кода и проверено.

## Что внутри

```
fixtures/              эталонные JSON-ответы всех эндпоинтов
  navigation.json      GET /navigation
  hero.json            GET /hero
  ...                  (17 файлов = 17 GET-эндпоинтов)
  articles/
    next-js-choice.json  GET /articles/next-js-choice
schemas.py             Pydantic-схемы — зеркало src/lib/types.ts
validate_fixtures.py   проверка фикстур по схемам
```

## Как использовать

**1. Схемы.** `schemas.py` кладётся в `app/schemas/` — это готовые модели
ответов, менять их не нужно. Если поля ORM в snake_case, добавьте в базовую
модель `alias_generator=to_camel` и сериализуйте через `model_dump(by_alias=True)`.

**2. Фикстуры как сид.** Каждый файл — ровно то, что должен вернуть
соответствующий эндпоинт. Скрипт сида читает их и раскладывает по таблицам.
Критерий приёмки: после сида ответ API совпадает с фикстурой.

**3. Фикстуры как тест контрактов.** `validate_fixtures.py` уже проверяет
фикстуры по схемам. Замените чтение файла на запрос к своему эндпоинту —
получится тест совместимости с фронтом:

```python
payload = client.get("/api/hero").json()
TypeAdapter(s.Hero).validate_python(payload)
```

## Проверка

```bash
pip install pydantic
python validate_fixtures.py
# Все 18 фикстур валидны по схемам.
```

## Важно про брендинг

Фикстуры выгружены из текущих моков фронта, где брендинг **не сведён**:
подвал и логотип — KTS Studio, а тексты внутренних страниц — DEV Studio
(`info@dev.studio`, адрес в Чебоксарах). По решению заказчика верный вариант —
**KTS Studio**. При загрузке в БД тексты приводятся к нему; фикстуры
обновятся после того, как я поправлю моки на фронте.

## Как перегенерировать

Из корня фронт-репозитория:

```bash
npx tsx scripts/export-mocks.ts
```

Скрипт заново соберёт `fixtures/` из `src/lib/mock/*.ts`. Запускать после
любых правок моков.
